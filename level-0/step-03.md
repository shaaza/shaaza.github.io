## Overview

In Steps 1 and 2, you blinked an LED. A blinking LED is proof that you can control hardware, but it is not a computer. A computer has **input**, **processing**, **storage**, and **output**. In this step you will add all four by wiring up real-world peripherals to the RP2040.

By the end of this step, your breadboard will have a display, buttons, an SD card, and USB connectivity. You will have built something that looks and functions like a tiny computer — because it *is* one.

We switch to **MicroPython** for this step. The point is not to wrestle with C toolchains while learning peripheral protocols — it is to understand how digital communication buses work. MicroPython lets you iterate fast, see results immediately, and focus on the hardware.

## What You Will Learn

- GPIO: digital input and output, pull-up and pull-down resistors
- SPI: high-speed serial communication (display, SD card)
- I2C: two-wire serial communication (display, sensors)
- UART: asynchronous serial (debugging, inter-device communication)
- Interrupts vs. polling: two fundamentally different approaches to responding to events
- How a "computer" is just a processor with the right peripherals attached

## Communication Protocols

Every peripheral talks to the RP2040 over one of a few standard protocols. Understanding these protocols is understanding how all digital devices communicate.

| Protocol | Wires | Speed | Direction | Use Cases |
|---|---|---|---|---|
| **GPIO** | 1 per signal | N/A (direct) | In or Out | LEDs, buttons, simple signals |
| **SPI** | 4 (MOSI, MISO, SCK, CS) | Up to 62.5 MHz | Full duplex | Displays, SD cards, flash memory |
| **I2C** | 2 (SDA, SCL) | 100–400 kHz typical | Half duplex | Sensors, small displays, EEPROMs |
| **UART** | 2 (TX, RX) | 9600–115200 baud typical | Full duplex | Debug consoles, GPS, Bluetooth modules |
| **USB** | 2 (D+, D-) | 12 Mbps (Full Speed) | Half duplex | Keyboards, mice, mass storage |

### SPI (Serial Peripheral Interface)

SPI uses four wires and a clock signal generated by the controller (your RP2040). On every clock pulse, one bit is transferred in each direction simultaneously. This makes SPI fast and predictable, but it requires a separate chip-select (CS) wire for every device on the bus.

```
Controller (RP2040)           Peripheral (Display)
   MOSI  ──────────────────>  DIN    (data in)
   MISO  <──────────────────  DOUT   (data out)
   SCK   ──────────────────>  CLK    (clock)
   CS    ──────────────────>  CS     (chip select, active low)
```

### I2C (Inter-Integrated Circuit)

I2C uses only two wires shared by all devices on the bus. Each device has a unique 7-bit address. The controller sends the address first, and only the addressed device responds. This saves wires but is slower than SPI.

```
Controller (RP2040)
   SDA  ──────┬──────┬──────  (data line, shared)
   SCL  ──────┼──────┼──────  (clock line, shared)
              |      |
           Device   Device
           addr=0x3C addr=0x68
           (OLED)   (IMU)
```

### Interrupts vs. Polling

There are two ways to detect when something happens (a button press, data arriving, a timer expiring):

**Polling:** Check repeatedly in a loop.

```python
while True:
    if button.value() == 0:  # Check every iteration
        handle_press()
    time.sleep_ms(10)
```

**Interrupts:** Register a handler; the hardware calls it when the event occurs.

```python
def button_handler(pin):
    handle_press()

button.irq(trigger=Pin.IRQ_FALLING, handler=button_handler)

# Main loop can do other work — the handler fires automatically
while True:
    update_display()
```

Polling is simpler but wastes CPU cycles. Interrupts are efficient but introduce complexity (what if an interrupt fires while you are in the middle of updating shared data?). This tradeoff appears everywhere in computing, from microcontrollers to web servers.

## Project: Build a Minimal Workstation

Wire up all the peripherals above. Then write MicroPython programs that use them together.

### Phase 1: Display Output

```python
from machine import Pin, I2C
import ssd1306

i2c = I2C(0, scl=Pin(5), sda=Pin(4), freq=400000)
oled = ssd1306.SSD1306_I2C(128, 64, i2c)

oled.fill(0)
oled.text("Hello from", 0, 0)
oled.text("Level 0!", 0, 16)
oled.text("Step 3", 0, 32)
oled.show()
```

Every pixel on the display is a bit in a buffer. `oled.show()` sends the entire 128x64-bit buffer (1024 bytes) over I2C to the display controller. The SSD1306 chip on the display interprets those bytes and drives the OLED pixels.

### Phase 2: Button Input

```python
from machine import Pin
import time

buttons = {
    'up':     Pin(10, Pin.IN, Pin.PULL_UP),
    'down':   Pin(11, Pin.IN, Pin.PULL_UP),
    'left':   Pin(12, Pin.IN, Pin.PULL_UP),
    'right':  Pin(13, Pin.IN, Pin.PULL_UP),
}

while True:
    for name, btn in buttons.items():
        if btn.value() == 0:  # Active low — pressed
            print(f"Button pressed: {name}")
    time.sleep_ms(50)  # Debounce delay
```

Note `Pin.PULL_UP` — this enables an internal pull-up resistor. Without it, the pin floats between 0 and 1 when the button is not pressed, giving random readings. The pull-up holds the pin at 1 (high); pressing the button connects it to ground (0).

### Phase 3: SD Card Storage

```python
from machine import Pin, SPI
import sdcard
import os

spi = SPI(0, baudrate=1000000, polarity=0, phase=0,
          sck=Pin(18), mosi=Pin(19), miso=Pin(16))
cs = Pin(17, Pin.OUT)

sd = sdcard.SDCard(spi, cs)
os.mount(sd, '/sd')

# Write a file
with open('/sd/log.txt', 'w') as f:
    f.write('Sensor reading: 42\n')

# Read it back
with open('/sd/log.txt', 'r') as f:
    print(f.read())

# List files
print(os.listdir('/sd'))
```

The SD card speaks SPI. The `sdcard` driver handles the SD protocol (commands, initialization sequence, block reads/writes). The filesystem on the card is FAT — the same format used by cameras and older USB drives.

### Phase 4: Putting It Together

Combine all peripherals into a single program:

```python
from machine import Pin, I2C, SPI
import ssd1306
import sdcard
import os
import time

# Initialize display
i2c = I2C(0, scl=Pin(5), sda=Pin(4), freq=400000)
oled = ssd1306.SSD1306_I2C(128, 64, i2c)

# Initialize buttons
btn_up = Pin(10, Pin.IN, Pin.PULL_UP)
btn_down = Pin(11, Pin.IN, Pin.PULL_UP)
btn_select = Pin(13, Pin.IN, Pin.PULL_UP)

# Initialize SD card
spi = SPI(0, baudrate=1000000, sck=Pin(18), mosi=Pin(19), miso=Pin(16))
sd = sdcard.SDCard(spi, Pin(17, Pin.OUT))
os.mount(sd, '/sd')

# File browser
files = os.listdir('/sd')
cursor = 0

def draw_menu():
    oled.fill(0)
    oled.text("== FILES ==", 0, 0)
    for i, f in enumerate(files[:5]):  # Show up to 5 files
        prefix = ">" if i == cursor else " "
        oled.text(f"{prefix} {f}", 0, 12 + i * 10)
    oled.show()

draw_menu()

while True:
    if btn_up.value() == 0:
        cursor = max(0, cursor - 1)
        draw_menu()
        time.sleep_ms(200)
    if btn_down.value() == 0:
        cursor = min(len(files) - 1, cursor + 1)
        draw_menu()
        time.sleep_ms(200)
    if btn_select.value() == 0:
        # Display file contents
        oled.fill(0)
        with open(f'/sd/{files[cursor]}', 'r') as f:
            for i, line in enumerate(f.readlines()[:6]):
                oled.text(line.strip()[:16], 0, i * 10)
        oled.show()
        time.sleep_ms(500)
```

This is a file browser. It reads the SD card, displays filenames on the OLED, lets you scroll with buttons, and shows file contents when you select. It is crude — but it is a functional computer interface built from a $4 chip and some wires.

## Stretch Goal: Shell on LCD

Build a minimal command shell that:

## Exercises

1. **Measure I2C speed.** Toggle a GPIO pin before and after `oled.show()`. Use an oscilloscope or logic analyzer (or just a timing loop) to measure how long it takes to transfer the full display buffer. Calculate the effective data rate and compare to the theoretical I2C bus speed.

2. **Add a rotary encoder.** Read the quadrature signals from a rotary encoder. Use it for scrolling instead of buttons.

3. **Implement debouncing.** Without the `time.sleep_ms(200)` after button reads, what happens? Implement proper debouncing — either with a timer or by tracking state transitions.

4. **SPI vs. I2C display.** If you have an SPI OLED, connect it and measure the display refresh time. How much faster is SPI than I2C for the same display?

5. **Interrupt-driven buttons.** Rewrite the button handling to use interrupts instead of polling. What advantages does this give you? What new problems does it introduce?

## Key Takeaways

- A "computer" is a processor plus peripherals for input, output, and storage
- SPI and I2C are the two most common protocols for embedded peripherals — learn them once and they apply everywhere
- Pull-up/pull-down resistors are not optional — floating pins give unpredictable results
- Interrupts are more efficient than polling but introduce concurrency concerns
- Every device on your desk — keyboard, monitor, SSD — communicates with the CPU through protocols just like these, at a higher speed and with more abstraction
